# Orbit Workspace

Orbit is a multi-role project workspace with a public landing page, email/password accounts, Google sign-in, a personal project manager, account security settings, and a dedicated administrator console.

The repository includes two AWS deployment paths. The recommended resume demo is a single EC2 instance with SQLite, ECR, Systems Manager, CloudFront, Terraform, and GitHub Actions OIDC. The optional EKS path is a larger, billable platform demonstration with RDS, Helm, Argo CD, Prometheus, and Grafana. The single-instance demo is the path intended for a Free Tier-focused account; AWS account eligibility and actual charges still need to be checked before apply.

## What’s included

- Separate user and admin routes, with server-side role checks on every protected API.
- Email/password registration and login, bcrypt password hashes, Google ID-token verification, and signed JWT sessions in `HttpOnly`, `SameSite=Lax` cookies.
- Origin checks for state-changing requests, authentication rate limits, secure headers, suspended-account session revocation, and production secret validation.
- User dashboard, profile/security/notification settings, searchable and filterable paginated project CRUD.
- Admin metrics and charts, paginated member CRUD, role and account-status controls, audit logs, and global registration/maintenance/auth settings.
- A seeded SQLite database so the interface is usable locally without an external service. Sample activity fills otherwise-empty chart periods.

## macOS setup

Install Homebrew if needed, then install Node.js (20.19 or newer) and npm:

```bash
brew install node
node --version
npm --version
```

From the repository root, set up the local environment and database:

```bash
cp .env.example .env
```

Edit `.env` and replace `JWT_SECRET` with a value generated by:

```bash
openssl rand -base64 48
```

Then install dependencies and create the SQLite database with sample accounts and projects:

```bash
npm install
npm run db:setup
```

Start the API and Vite hot-reload server together:

```bash
npm run dev
```

Open `http://localhost:5173`. Vite proxies `/api` to the Express API on port `4000`.

### Local demo accounts

The development seed creates these accounts:

| Role | Email | Password |
| --- | --- | --- |
| User | `user@orbit.local` | `UserDemo!2026` |
| Admin | `admin@orbit.local` | `AdminDemo!2026` |

Change these credentials before using any non-development environment. Production seeding rejects the default admin credentials.

### Google sign-in setup

Google sign-in is optional for local email/password use. To enable it:

1. Create an OAuth 2.0 **Web application** client in Google Cloud Console and configure the consent screen.
2. Add `http://localhost:5173` as an authorized JavaScript origin.
3. Set the same client ID in both `GOOGLE_CLIENT_ID` and `VITE_GOOGLE_CLIENT_ID` in `.env`.
4. Restart `npm run dev`.

The browser sends Google's ID token to Express. Express verifies its signature, audience, and verified-email claim with Google's library before creating a local session. Orbit never stores the JWT in browser storage.

## Testing and release checks

Run the production frontend build and check the API health endpoint:

```bash
npm run build
curl http://localhost:4000/api/health
```

Then manually check the key flows in the local browser:

1. Sign in as the demo user; confirm `/admin` redirects to `/app` and the user only sees their own projects.
2. Create, search, filter, edit, paginate, and delete projects; refresh to confirm changes persist.
3. Save profile, password, and notification settings; sign out and sign back in.
4. Sign in as the demo admin; promote/demote, suspend/reactivate, edit, create, and delete accounts. Confirm the final active admin cannot remove their own access.
5. Filter the audit trail and confirm authentication, project, account, and configuration actions appear.
6. Toggle registrations, Google-required admin sign-in, and maintenance mode; verify each setting changes the corresponding server behavior.
7. If configured, sign in and link an account through Google. Confirm the server rejects an invalid or unverified Google credential.

SQLite is used for local development and the single-instance EC2 demo. The optional EKS chart runs multiple stateless app replicas against shared PostgreSQL in RDS. Production JWTs remain in secure HTTP-only cookies; EKS secrets are read from AWS Secrets Manager through External Secrets Operator.

## AWS single-instance demo deployment

This is the selected path for a Free Tier-focused resume demo. It uses one `t3.micro` EC2 instance, an encrypted 16 GiB EBS volume with SQLite, ECR, Systems Manager, a small VPC, GitHub Actions OIDC, and a CloudFront default HTTPS hostname. GitHub Actions builds and scans the image, pushes it to ECR, then asks Systems Manager to deploy it. There is no SSH key or public SSH port. CloudFront is the only allowed path to the app port.

It is a working demo, not a highly available production service: one instance and one SQLite database mean downtime and data loss are possible if that instance or its volume is lost. This path omits EKS, RDS, NAT Gateway, ALB, Prometheus, and Grafana to avoid their baseline costs.

With the default CloudFront hostname, visitor traffic uses HTTPS to CloudFront but CloudFront uses HTTP to the EC2 origin. Use dedicated demo accounts and no real or sensitive data on this route. A real production deployment needs an owned domain and HTTPS to the origin.

AWS Free Tier eligibility varies with account plan and account age. The EC2 instance, public IPv4, EBS, ECR image storage, CloudFront traffic, and data transfer can cost money if not covered by the account's current offer or credits. AWS documents the current EC2 eligibility by account age in its [Free Tier usage guide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-free-tier-usage.html). Public IPv4 can be billed at $0.005/hour outside eligible allowances ([AWS announcement](https://aws.amazon.com/blogs/aws/new-aws-public-ipv4-address-charge-public-ip-insights/)); CloudFront includes monthly request and transfer allowances on its pay-as-you-go plan, with overages billed ([CloudFront FAQ](https://aws.amazon.com/cloudfront/faqs/)). Check the account's current plan and billing dashboard before applying.

Follow the complete setup in [infra/ec2-demo/README.md](infra/ec2-demo/README.md). It covers AWS CLI SSO, Terraform variables, applying the stack, setting GitHub Actions repository variables, the CloudFront URL, Session Manager, and cleanup. The Terraform plan is the review step; do not apply until you have checked which charges your account's Free Tier or credits cover.

## Optional AWS EKS deployment

The EKS implementation is retained as an optional advanced portfolio path. Its deploy workflow is manual and it is not the default deployment. EKS does not fit a strict Free Tier-only budget: the cluster charge is about $73/month at the standard $0.10/hour rate before worker nodes, NAT Gateway, RDS, ALB, and other usage. See current [AWS EKS pricing](https://aws.amazon.com/eks/pricing/) before using it.

### What Terraform creates

- A VPC across two Availability Zones, private worker/database subnets, one NAT gateway, VPC flow logs, and a public ALB security group that accepts requests only from CloudFront edge ranges.
- A managed EKS control plane and private managed worker nodes, with EKS API access limited to the CIDRs you specify, plus EBS CSI for encrypted persistent `gp3` volumes.
- A private encrypted PostgreSQL RDS instance, ECR repository, Secrets Manager entries, service-account IAM roles, and an IAM role that GitHub Actions assumes through OIDC.
- An optional CloudFront distribution with HTTPS for visitors. CloudFront forwards requests to the ALB over HTTP because the default CloudFront hostname cannot be used to issue an ALB certificate. A per-distribution secret header is verified by the application.

Helm installs AWS Load Balancer Controller, External Secrets Operator, Cluster Autoscaler, Metrics Server, Argo CD, and kube-prometheus-stack (Prometheus/Grafana). Prometheus, Grafana, and Alertmanager store their data on encrypted `gp3` volumes. The Orbit Helm chart provides two app replicas, probes, HPA, a PDB, and a pre-sync PostgreSQL migration Job. Argo CD owns the app rollout after its Application is created.

### Requirements and accounts

Use an AWS account with permissions to create EKS, VPC, EC2, RDS, ECR, IAM/OIDC, Secrets Manager, CloudFront, and CloudWatch resources. Use AWS IAM Identity Center/SSO if available; do not place long-lived AWS keys in the repository or GitHub.

Install tools on macOS:

```sh
brew install awscli kubectl helm terraform
aws --version
terraform version
kubectl version --client
helm version
```

Configure your AWS CLI profile using your organization's SSO setup, then verify that the intended account is selected:

```sh
aws configure sso
aws sso login
aws sts get-caller-identity
```

Create an empty GitHub repository and push this project to its `main` branch. Terraform needs the repository's `OWNER/REPOSITORY` name so its OIDC role trusts only that repository and branch. No repository remote is configured in this local folder yet.

### 1. Create remote Terraform state storage

Choose a globally unique lowercase S3 bucket name. The bootstrap stack creates a private, versioned, encrypted bucket. Its own state remains local, so keep that local state private and back it up securely.

```sh
terraform -chdir=infra/bootstrap init
terraform -chdir=infra/bootstrap apply \
  -var='state_bucket_name=orbit-tfstate-YOUR_UNIQUE_SUFFIX' \
  -var='aws_region=ap-south-1'
```

Create the platform backend configuration from the example and set its bucket to the bootstrap output:

```sh
cp infra/terraform/backend.hcl.example infra/terraform/backend.hcl
```

Edit `infra/terraform/backend.hcl`, then create the ignored Terraform variable file:

```sh
cp infra/terraform/terraform.tfvars.example infra/terraform/terraform.tfvars
```

Set `github_repository` to your `OWNER/REPOSITORY`, and set `cluster_admin_cidrs` to your current public IPv4 address followed by `/32`. Get your address with `curl -4 https://checkip.amazonaws.com`. Keep the CIDR narrow; the EKS control plane API is not opened to the internet.

Initialize and review the exact planned AWS resources and costs before applying:

```sh
terraform -chdir=infra/terraform init -backend-config=backend.hcl
terraform -chdir=infra/terraform validate
terraform -chdir=infra/terraform plan
terraform -chdir=infra/terraform apply
```

The deployment defaults use two `t3.large` nodes, one NAT gateway, a small single-AZ RDS PostgreSQL instance, and a continuously running EKS control plane. EKS control-plane charges alone are about $73/month at the standard $0.10/hour rate; compute, NAT, RDS, ALB, data transfer, logs, and CloudFront add to that. Rates vary by region and usage. Review the estimate in your plan and the [AWS Pricing Calculator](https://calculator.aws/#/estimate) before applying. Check [EKS pricing](https://aws.amazon.com/eks/pricing/), [VPC pricing](https://aws.amazon.com/vpc/pricing/), and [RDS PostgreSQL pricing](https://aws.amazon.com/rds/postgresql/pricing/).

### 2. Configure CI/CD and publish the first image

Read the Terraform outputs:

```sh
terraform -chdir=infra/terraform output
```

In the GitHub repository, add these **Actions variables** (Settings → Secrets and variables → Actions → Variables):

| Variable | Value |
| --- | --- |
| `AWS_REGION` | Terraform `aws_region` output |
| `AWS_DEPLOY_ROLE_ARN` | Terraform `github_deploy_role_arn` output |
| `ALB_SECURITY_GROUP_ID` | Terraform `load_balancer_security_group_id` output |
| `VITE_GOOGLE_CLIENT_ID` | Leave empty unless OAuth has been configured for an owned public domain |

Manually run **Deploy EKS platform (billable alternate)** from the Actions tab on `main`. The workflow builds the image, scans it for critical/high vulnerabilities, pushes an immutable SHA tag to ECR using short-lived OIDC credentials, and updates `deploy/chart/values-prod.yaml`. It never receives static AWS keys. The regular CI workflow builds pull requests and `main` pushes; the EC2 workflow deploys on `main` changes.

### 3. Install platform controllers and connect GitOps

After Terraform is applied and the first image workflow has finished, install the cluster add-ons:

```sh
scripts/install-platform.sh
```

Then point Argo CD at your repository:

```sh
scripts/apply-gitops-app.sh YOUR_GITHUB_OWNER/YOUR_REPOSITORY
kubectl get applications -n argocd
kubectl get pods -n orbit
kubectl get ingress -n orbit
```

The `orbit-workspace` Argo CD Application watches `main` and deploys `deploy/chart`. New commits trigger the image build; Argo CD observes the updated SHA tag and rolls out the new release. The migration Job runs before each app sync.

### 4. Add CloudFront HTTPS and create the first administrator

Wait for the ingress to show an ALB hostname, then create CloudFront and update the app's allowed browser origin:

```sh
scripts/configure-cloudfront-origin.sh
```

After it prints the CloudFront hostname, bootstrap an admin with a unique password. The script prompts for the password without echoing it and removes the temporary Kubernetes secret and Job afterward:

```sh
scripts/bootstrap-admin.sh
```

Open the HTTPS CloudFront hostname, register or sign in, and use your administrator account for the admin workspace. CloudFront and the ALB origin are not created until you run the Terraform steps above.

### 5. Open dashboards privately

Argo CD and Grafana stay internal to the cluster. Use port-forwarding rather than exposing their admin endpoints:

```sh
kubectl -n argocd port-forward svc/argo-cd-argocd-server 8080:443
```

Open `https://localhost:8080`. Retrieve the initial Argo CD password only when needed:

```sh
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath='{.data.password}' | base64 --decode
```

In a second terminal:

```sh
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80
```

Use the Grafana admin credentials stored in AWS Secrets Manager (`orbit-production/grafana`); retrieve them in the AWS Console or with your authenticated CLI session. Prometheus alert rules cover unavailable Orbit replicas and sustained replica shortfalls.

### Google sign-in and the CloudFront hostname

The AWS deployment uses CloudFront's HTTPS hostname as requested. Google OAuth production clients require a domain you control and verify, so Google sign-in is intentionally unavailable on `*.cloudfront.net`. Email/password authentication works after the CloudFront origin is configured. To enable Google sign-in in production, attach a domain you own to CloudFront, verify it in Google Auth Platform, add that HTTPS origin to the OAuth client's authorized JavaScript origins, set the same client ID in Terraform (`google_client_id`) and the GitHub Actions variable (`VITE_GOOGLE_CLIENT_ID`), then deploy again. See Google's [OAuth production readiness requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).

### Cost cleanup

The Terraform stack enables deletion protection for EKS and RDS and keeps ECR images. To tear the environment down, first review and update the protection settings in `infra/terraform/main.tf`, apply those changes, remove ECR images, then run `terraform destroy`. Keep the separate state bucket until the platform state is no longer needed. RDS snapshots and Secrets Manager recovery windows can continue to incur charges during retention.

### Deployment status

This repository contains deployment configurations, but no AWS resources have been created from them. The local environment currently has no AWS CLI/profile and no Git remote URL has been provided. Configure AWS SSO, provide the GitHub repository URL, and review the AWS Free Tier/credits and Terraform plan before the first apply.
